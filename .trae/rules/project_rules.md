# 项目规则

## 基本原则
- 这是企业级项目，所有代码修改都必须以稳定性、可维护性、兼容性和可扩展性为优先，禁止为了快速完成需求而采用明显不稳妥的实现。
- 在开始修改前，必须先理解现有实现、上下游依赖、调用链路、数据结构、接口契约以及可能受影响的模块，不能只针对单点文件做孤立修改。
- 当需求本身存在设计风险、兼容性风险、扩展性不足或实现方式不稳妥时，必须明确指出问题，并给出更稳妥的替代方案，供用户选择后再继续实施。
- 不能机械执行指令，必须结合项目上下文进行独立思考、风险判断和方案权衡。
- 任何涉及公共能力、基础设施、数据结构、对外接口、公共组件的改动，都必须默认按高风险变更处理，先评估再实施。

## 注释规范
- 编写或修改代码时，需要提供清晰、规范、专业的注释。
- 每个新增或修改的接口、类、方法都必须有注释，说明其用途、适用场景、关键行为、必要时说明参数、返回值、异常和注意事项。
- 对关键业务逻辑、边界条件处理、兼容性处理、降级逻辑、特殊判断等内容，必须补充必要注释，确保后续维护人员能够快速理解设计意图。
- 注释内容必须准确、克制、与实现一致，禁止写空泛注释、误导性注释或与代码不符的注释。
- 当实现中存在业务约束、历史兼容逻辑、特殊数据约定、平台限制时，必须在代码中明确标注原因，避免后续误改。

## 修改代码前的检查要求
- 必须先检查目标方法、接口、类是否被其他模块、服务、控制器、定时任务、前端页面、导入导出流程、第三方调用或配置流程引用。
- 涉及公共方法、公共字段、枚举、数据库字段、接口入参与返回结构时，必须优先评估兼容性影响。
- 如果直接修改原方法会影响已有调用方、历史数据、已有接口契约或已有业务流程，应优先考虑保留原逻辑并新增更稳妥的方法、重载方法或适配层，而不是粗暴覆盖旧逻辑。
- 涉及数据库、缓存、消息、文件、导入导出、外部接口、权限、事务、并发处理时，必须额外评估风险点。
- 删除、重命名、移动公共方法、公共类、接口路径、字段名称、枚举值、常量值前，必须全局检查引用关系，确认影响范围后才能调整。
- 涉及前后端联动的字段、接口、状态值、字典值、文件路径、下载导出结构时，必须同时检查前端页面、后端接口、数据库和历史数据兼容性。

## 兼容性与设计要求
- 所有改动都必须优先考虑向后兼容，避免影响已有功能、已有接口调用方和已有数据。
- 若存在潜在破坏性变更，必须先明确告知风险，再提出兼容方案、折中方案和理想方案。
- 对于无法保证兼容性的改动，不得直接实施，应先与用户确认。
- 对已有功能进行增强时，优先采用增量式改造，尽量避免整体推翻重写；但若原设计明显不合理，也应明确说明原因，并提出更合理的新方案。
- 公共接口的入参、出参、字段语义、状态码、错误码、排序规则、分页结构应尽量保持稳定；如必须调整，必须提供兼容策略。
- 对数据库字段含义、默认值、状态枚举、字典值的修改必须谨慎，不能只看当前页面是否可用，还要考虑历史数据、导入导出、报表、定时任务和其他隐式依赖。
- 涉及导入、导出、批处理、定时任务、异步任务时，必须考虑历史模板、历史文件、旧数据和重复执行的兼容性问题。
- 涉及配置项改动时，必须区分本地开发、测试、生产、容器部署等不同环境，不能把某一环境的假设直接套到所有环境。

## 方法设计要求
- 方法职责要单一，命名要准确，避免一个方法承担过多业务逻辑。
- 参数校验必须完整，尤其是接口入参、公共方法入参、DTO/VO/Query对象中的关键字段、分页参数、状态参数、时间参数、集合参数等。
- 对空值、越界值、非法状态、格式错误、重复提交、并发场景、异常分支要有合理处理，不能默认外部一定传对。
- 错误处理要明确，提示信息要可理解，不能吞异常、不能静默失败、不能返回语义不清的结果。
- 若现有方法设计不合理、难以兼容或继续堆逻辑会导致维护性变差，应优先新增更清晰的方法，并保留旧方法兼容已有调用方。
- 新增方法前，应先判断是扩展现有抽象更合理，还是新增独立能力更合理，避免因为临时需求造成接口层级混乱。
- 对公共方法应优先设计清晰的入参边界和返回语义，避免让调用方依赖隐式约定。

## 数据库与数据安全要求
- 任何数据库相关改动都必须优先确认字段语义、索引影响、历史数据兼容性、空值处理和回滚难度。
- 不能随意修改数据库字段含义，不能在未评估历史数据影响前调整字段类型、长度、默认值和状态定义。
- 涉及删除数据、批量更新、覆盖写入、状态回写时，必须评估误操作风险，并尽量采用可回滚、可审计、可追踪的实现方式。
- 涉及敏感信息、凭证、密钥、用户隐私数据时，禁止输出到日志、导出文件、异常信息或调试信息中。

## 接口与前后端协同要求
- 新增或修改接口时，必须检查权限标识、参数校验、返回结构、异常处理、前端调用方式和接口文档一致性。
- 不能随意改变前端已依赖的字段名称、布尔语义、状态值格式、时间格式、文件地址格式。
- 若确实需要调整接口结构，应优先新增兼容字段、保留旧字段一段时间，或新增版本化接口，而不是直接替换。
- 涉及文件上传、下载、预览、富文本、导入、导出时，必须考虑不同环境下的访问路径、代理前缀、资源前缀和历史数据格式。

## 实施过程要求
- 修改前要先分析影响范围；修改后要检查关联代码是否需要同步调整。
- 不能只完成表面需求，必须检查相关调用链、配置项、枚举值、前后端交互、数据库映射、导出导入逻辑、权限标识、校验逻辑是否需要联动修改。
- 如果发现用户提出的方案存在不妥之处，应主动说明原因，并给出更优方案，而不是直接照做。
- 在提供实现方案时，应优先给出稳妥、可维护、易扩展的方案；必要时可同时说明简单方案和推荐方案之间的差异。
- 对复杂修改，应先拆分步骤，必要时先完成无破坏性的重构、抽取、隔离，再实施业务变更。
- 涉及旧逻辑替换时，应优先考虑灰度兼容、保底分支、降级处理或显式兜底，而不是一步到位直接切换。

## 质量要求
- 所有提交的修改都应尽量保证代码风格统一、结构清晰、命名规范、层次分明。
- 避免引入重复代码；如果出现重复逻辑，应优先考虑抽取复用。
- 避免引入隐式副作用，避免因为修复一个问题而破坏另一个流程。
- 修改完成后，应主动检查是否存在明显的不妥设计、潜在空指针、边界缺失、兼容性问题和可维护性问题。
- 能做校验时，必须进行必要的校验、静态检查、编译检查或相关验证；如果受环境限制无法执行，也要明确说明未验证项和潜在风险。
- 对关键链路改动，至少要说明验证思路、核心场景和容易遗漏的边界情况。
- 如果当前环境无法完成完整验证，必须明确说明哪些结论已验证、哪些尚未验证、哪些风险仍需用户关注。

## 禁止事项
- 禁止在未分析影响范围前直接修改公共接口、公共方法、数据库字段语义、状态枚举和导出导入模板。
- 禁止为了省事而写死路径、环境参数、状态值、用户数据、租户数据、文件地址或部署假设。
- 禁止在不明确调用方影响的情况下直接删除、重命名或覆盖旧逻辑。
- 禁止吞异常、绕过校验、跳过权限、弱化事务边界、忽略并发问题。
- 禁止只为了满足当前页面显示而破坏数据一致性、接口稳定性或历史兼容性。

## 沟通要求
- 如果需求存在歧义、实现路径不唯一、风险较高或可能影响现有系统稳定性，应先沟通确认再实施。
- 如果用户方案不是最优解，应明确指出问题，并给出更好的替代方案，而不是默认按原方案直接落地。
- 回答问题时，不仅要说明"怎么改"，还要说明"为什么这样改""有哪些风险""是否有更稳妥的选择"。
- 对于存在权衡的问题，应尽量给出推荐方案、兼容方案和简单方案的区别，帮助用户做决策。

## 前端开发规范

### 框架与依赖
- 本项目前端基于 RuoYi-Vue（Vue 2 + Element UI），不得引入与现有技术栈冲突的第三方 UI 库。
- 使用已有的 `@/utils/request` 进行接口调用，`@/api/` 目录统一管理 API 定义。
- 字典数据通过 `dicts` 选项声明，模板中使用 `dict.type.xxx` 访问。
- 部门树使用 `@riophae/vue-treeselect`，统一用 `listDept` API 加载。

### 表单只读字段展示规范
- 禁止在 el-form 内使用裸 `<span>` 展示只读字段，这会导致与周边 input/select 组件视觉断裂，破坏表单纵向对齐。
- 只读字段必须使用 `<el-input :value="xxx" disabled />`，保持与表单其他字段统一的边框、高度、内边距和字体。
- 如果只读字段需要特殊视觉效果（如状态标签），使用 `<dict-tag>` 或 `<el-tag>` 包裹在 `el-form-item` 内，但需保证垂直对齐。

### 操作列规范
- 表格操作列宽度不应超过 200px；如果操作项超过 3 个，优先使用 `el-dropdown` 收纳次要操作。
- `el-dropdown` 的触发按钮样式必须与同一列的其他 `el-button type="text"` 保持一致（size="mini" type="text"）。
- 废弃/删除等不可逆操作应加确认弹窗（`this.$modal.confirm`），操作后必须刷新列表并提示结果。
- 操作按钮的显隐根据数据行状态动态控制，不可用的操作直接隐藏而非置灰。

### 弹窗内编辑表单布局规范
- 编辑表单统一使用 `el-row` + `el-col`（`:span="12"` 或 `:span="24"`）做双列布局。
- 所有表单控件统一 `style="width: 100%"`，禁止出现宽度不一致的控件。
- 弹窗表单的 `label-width` 统一为 `"110px"`，保持与项目已有页面一致。
- 表单的 `el-form-item` 必须绑定 `prop` 和 `rules` 校验规则，不得依赖后端兜底。
- 弹窗 footer 统一为右对齐，按钮顺序为 [确定] [取消]（primary 在前）。

### 业务操作弹窗规范
- 领用、归还、调拨、报废等业务操作弹窗，必须在表单上方展示当前操作对象的关键信息（如资产编号、资产名称、当前状态、当前归属），让操作人明确知道在操作哪个资产。
- 信息展示区域使用 `el-descriptions` 组件或 `el-card` 包裹的摘要行，配色使用浅灰背景，与下方表单区分。
- 操作弹窗标题必须明确包含操作类型（如"资产领用 - XXXX"），而非泛化的"操作"。
- 原因/备注字段统一为必填，校验提示要具体（如"请输入领用原因"而非"原因不能为空"）。

### 时间线与日志展示规范
- 流转记录、操作日志等时间线内容，使用 `el-timeline` + `el-timeline-item` 展示。
- 每条时间线节点包含：操作类型标签（`el-tag`）、状态变更摘要、关键字段 before/after 对比、操作原因、操作时间。
- 不同类型使用不同颜色的 timeline node 和 tag：领用=primary、归还=success、调拨=warning、报废=danger、信息变更=info。
- 当记录为空时，使用 `el-empty description="暂无记录"` 展示空状态。

### 按钮图标规范
- 新增：`icon="el-icon-plus"`、type="primary"
- 修改：`icon="el-icon-edit"`、type="success"
- 删除：`icon="el-icon-delete"`、type="danger"
- 导出：`icon="el-icon-download"`、type="warning"
- 查看/详情：`icon="el-icon-view"`、type="info"
- 流转记录：`icon="el-icon-s-order"`、type="info"
- 领用：`icon="el-icon-check"`、type="primary"
- 归还：`icon="el-icon-refresh-left"`、type="success"
- 调拨：`icon="el-icon-sort"`、type="warning"
- 报废：`icon="el-icon-close"`、type="danger"

### 样式规范
- 禁止在模板中大量使用内联 `style`；除少量必要情况外，统一使用 `<style scoped>` 中的 class 选择器。
- 搜索区域使用 `search-card` class + `search-control` class，与项目已有页面保持一致。
- 同一页面内不得出现多种不同风格的间距、字号、颜色方案。
- 新增 class 命名采用 kebab-case，避免驼峰命名。

### el-table 固定列规范
- 禁止在列数多、无横向滚动需求的表格上使用 `fixed="left"` 或 `fixed="right"`。
- `fixed` 属性会让 Element UI 创建独立的绝对定位 `<table>`，导致固定列与非固定列的行高不一致，产生割裂感。
- 只有在表格列数超过可视区域、必须横向滚动时才使用 `fixed`，且此时必须同时设置 `:row-height` 保证行高统一。
- 非固定列场景直接使用 `width` 或 `min-width`，让列跟随表格自然布局。

## 写完必提交Git

每次写完后，必须执行：
1. `git add -A`
2. `git commit -m "描述本次改动"` feat:xxx fix: refactor:xxx 要是这样的格式
3. `git push`
不能遗漏，不能攒多次一起提交。
